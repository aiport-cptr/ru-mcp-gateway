# Установка ru-mcp-gateway — инструкция для ИИ-помощника

Ты устанавливаешь корпоративный MCP-шлюз на сервер пользователя по [INSTALL.md](INSTALL.md).
Сервер может быть рабочим: на нём бывают чужие сайты, контейнеры и базы. Твоя задача — поставить
шлюз, ничего чужого не задев, и не увидеть ни одного секрета.

## Правила (обязательны)

1. **Секреты не запрашивай и не принимай.** Пароли, токены, ключи, Client secret, содержимое `.env`
   пользователь вписывает сам на сервере (`sudo nano /opt/rugw/.env`). Если он прислал секрет
   в чат — не используй его, попроси сменить этот секрет и вписать новый сам.
2. **Секреты не выводи.** Не выполняй `cat .env`, `grep` по `.env`, `env`, `printenv`,
   `docker compose config`, `docker inspect` с переменными окружения и аналоги. Проверить,
   заполнено ли поле, можно без значения:
   `sudo awk -F= '$1=="RUGW_YANDEX_CLIENT_SECRET"{print ($2==""?"пусто":"заполнено")}' /opt/rugw/.env`.
   Настройки проверяет `deploy/check.sh` — он значений не печатает.
3. **Не разрушай.** Никогда: `docker compose down -v`, `docker volume rm`, `docker system prune`,
   `rm` в `/opt/rugw/backups`, остановка или правка чужих контейнеров. Команды Compose выполняй
   только в `/opt/rugw` (проект `rugw`).
4. **Чужие настройки — только с подтверждением.** Файлы nginx/Caddy, файрвол, DNS, cron: покажи
   пользователю, что именно и куда добавишь, и дождись согласия. Перед перезагрузкой nginx —
   `nginx -t`, перед перезагрузкой Caddy — `caddy validate`. Если проверка не прошла — не
   перезагружай.
5. **Порт шлюза только на 127.0.0.1.** Не открывай его в файрволе и не меняй `ports` в
   `docker-compose.yml`. Наружу — только через HTTPS-прокси.
6. **Вход в шлюз не отключается.** Не пытайся обойти проверку настроек: если шлюз не стартует —
   исправляй настройки, а не код.

## Порядок

1. Осмотр без изменений: `uname -a`, `free -m`, `df -h /`, `docker compose version`,
   `sudo ss -ltnp` (кто занимает 80/443), `docker ps --format '{{.Names}}\t{{.Ports}}'`.
   Расскажи пользователю, что нашёл и каким способом будет HTTPS.
2. Спроси у пользователя (это не секреты): поддомен, email администратора, почтовые домены
   сотрудников. Убедись, что A-запись поддомена указывает на сервер.
3. INSTALL.md, шаги 1–2: `sudo deploy/install.sh --domain … --admin … --allowed-domains … --non-interactive`.
4. Шаг 3: попроси пользователя создать OAuth-приложение Яндекса (Redirect URI — из вывода
   установщика) и самому вписать ClientID и Client secret в `.env`. Затем снова `sudo deploy/install.sh --non-interactive`.
5. Шаг 4, если способ не `caddy`: по правилу 4.
6. `sudo deploy/check.sh` — все пункты с ✓.
7. Предложи пользователю ежедневную резервную копию (cron из INSTALL.md) и напомни сохранить
   `.env` в надёжное место самостоятельно.
8. Итог пользователю: адрес подключения `https://<домен>/mcp`, что первым входит администратор,
   какие коннекторы включены (из `check.sh`).

## Если не получается

Опиши пользователю симптом и вывод команды (без секретов) — таблица в конце INSTALL.md.
Не пробуй обходные пути, нарушающие правила выше.
