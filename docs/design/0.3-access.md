# 0.3: права на ресурсы и доступ от имени пользователя

## 1. Права на ресурсы

### Модель

Право (`resource_grants`) — это кортеж *кому → коннектор → ресурс → уровень*:

| Поле | Значения |
|---|---|
| `subject` | `role:readonly`, `role:member`, `user:ivan@company.ru` |
| `connector` | `tracker`, `bitrix24`, `onec` или `*` |
| `resource` | шаблон с `*`, формат зависит от коннектора (ниже) |
| `level` | `read` или `write` |

Итоговое право пользователя на ресурс = **минимум** из:
1. **потолка роли**: `readonly` → только read, `member` → read и write;
2. **максимума по подходящим правам** (своим `user:` и своей роли `role:`).

Нет подходящего права — нет доступа. Роль `admin` проверку ресурсов не проходит: у неё
доступ ко всему (иначе админ легко заблокирует сам себя).

Права пользователя к ресурсу — только расширяющие (allow). Запретов (deny) нет: так модель
проще проверить. Сузить доступ = удалить широкое право и выдать узкие.

### Совместимость

Миграция `0004` создаёт два права, повторяющих поведение 0.2:
`role:readonly * * read` и `role:member * * write`. Чтобы ограничить доступ, удалите их
(`rugw grants remove`) и выдайте узкие.

### Ресурсы по коннекторам

| Коннектор | Ресурс | Примеры |
|---|---|---|
| `tracker` | ключ очереди | `SUP`, `HR*`, `*` |
| `bitrix24` | `deal:<id воронки>`, `lead`, `contact`, `company` | `deal:0`, `deal:*`, `lead` |
| `onec` | имя набора OData | `Catalog_Контрагенты`, `Document_*` |

### Где проверяется

- **Список инструментов**: инструмент коннектора виден, только если у пользователя есть хоть
  одно право на этот коннектор нужного уровня.
- **До обращения во внешнюю систему**, когда ресурс известен из аргументов (ключ задачи
  `SUP-1` → очередь `SUP`; имя набора 1С; тип сущности Битрикс24).
- **После получения данных**, когда ресурс виден только в ответе: поиск в Трекере и список
  сделок Битрикс24 отфильтровываются по разрешённым очередям/воронкам; карточка сделки
  чужой воронки не отдаётся; комментарий в сделку пишется только после проверки её воронки.

Отказ по ресурсу пишется в аудит как `denied`.

Фильтрация после получения означает, что поиск может вернуть меньше записей, чем `limit`.
Это осознанный выбор: язык запросов Трекера и фильтры Битрикс24 нельзя надёжно проверить
до выполнения, а фильтр по уже полученным данным обойти нельзя.

## 2. Доступ от имени пользователя (Трекер)

`RUGW_TRACKER_AUTH_MODE`:
- `service` (по умолчанию) — как раньше: общий токен `RUGW_TRACKER_TOKEN`;
- `user` — запрос идёт с токеном Яндекса самого сотрудника. Тогда действуют и права шлюза,
  и права сотрудника в Трекере; в истории задачи автором комментария будет сотрудник.

Как это работает:
1. При входе шлюз просит у Яндекса дополнительные права из `RUGW_YANDEX_EXTRA_SCOPES`
   (например `tracker:read tracker:write`). Они должны быть включены в OAuth-приложении.
2. Токены Яндекса сохраняются в `user_credentials` **зашифрованными** (Fernet,
   ключи `RUGW_TOKEN_ENCRYPTION_KEYS`). Без ключа режим `user` не запускается.
3. При вызове инструмента токен расшифровывается в памяти; если истёк — обновляется
   по refresh-токену Яндекса и пересохраняется.
4. Нет сохранённого токена или Яндекс его отверг → инструмент просит войти заново.
5. `rugw users disable` удаляет сохранённые токены пользователя.

Согласованность (0.3.1, по итогам проверки): у записи есть поколение. Обновление по refresh
пишет результат условным UPDATE «если поколение не изменилось» и никогда не создаёт запись;
при конфликте (новый вход, удаление) результат отбрасывается. Вход пишет токены, только если
пользователь не заблокирован, под `SELECT … FOR UPDATE` строки пользователя.

Ротация ключа: в `RUGW_TOKEN_ENCRYPTION_KEYS` через запятую — новый ключ первым, старые
после него. Шифрование — первым ключом, расшифровка — любым. После перешифровки
(`rugw credentials rotate`) старый ключ можно убрать.

Яндекс 360 (почта, календарь, диск) от имени пользователя — в 0.4, на этой же основе.
