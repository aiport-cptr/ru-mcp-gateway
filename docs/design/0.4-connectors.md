# 0.4: диагностика и новые коннекторы

## 1. Коды ошибок и номер запроса

Каждый вызов инструмента получает номер `rq-<12 hex>`. При ошибке модель получает:

```
Трекер: ошибка HTTP 503 — сбой на стороне внешней системы [код UPSTREAM_ERROR, запрос rq-3f9a1c0b7e21]
```

Номер записывается в аудит (`audit_events.request_id`, миграция `0006`) и в лог сервера.
Администратор находит вызов командой `rugw audit list --request rq-…`.

Коды (`src/rugw/errors.py`) стабильны: новые добавляются, смысл существующих не меняется.

| Код | Когда |
|---|---|
| `BAD_INPUT` | некорректные аргументы инструмента |
| `ACCESS_DENIED` | нет прав в шлюзе (роль, коннектор, ресурс) |
| `RELOGIN_REQUIRED` | нужен повторный вход через Яндекс |
| `UPSTREAM_AUTH` | внешняя система отклонила учётные данные коннектора (401/403) |
| `UPSTREAM_NOT_FOUND` | 404 |
| `UPSTREAM_RATE_LIMIT` | 429 |
| `UPSTREAM_BAD_REQUEST` | прочие 4xx |
| `UPSTREAM_ERROR` | 5xx или ошибка в теле ответа (Битрикс24) |
| `UPSTREAM_TIMEOUT`, `UPSTREAM_UNAVAILABLE` | таймаут; сеть, DNS, TLS |
| `UPSTREAM_BAD_RESPONSE` | ответ не в ожидаемом формате |
| `INTERNAL` | ошибка в самом шлюзе; подробности — только в логе сервера по номеру запроса |

Сырые ответы внешних систем по-прежнему не передаются (см. разбор проверки 0.2).

Лог `httpx` на уровне INFO отключён: он писал полный адрес запроса, а в адресе бывают
секреты (вебхук Битрикс24, ключ Контур.Фокуса).

## 2. Трекер: связанные задачи

В карточке задачи вложенные ссылки на задачи (родитель, эпик, связи — любой вложенный объект
с `key` вида `QUEUE-123`) из очередей, недоступных пользователю, заменяются заглушкой.

## 3. Новые коннекторы

| Коннектор | Ресурсы для прав | Инструменты | Запись |
|---|---|---|---|
| `amocrm` | `lead:<id воронки>`, `contact`, `company` | `amocrm_leads_list`, `amocrm_lead_get`, `amocrm_contacts_list`, `amocrm_add_note` | только примечания |
| `moysklad` | `product`, `counterparty`, `customerorder`, `demand`, `supply`, `store`, `stock` | `moysklad_list`, `moysklad_stock` | нет |
| `focus` | метод: `req`, `egrDetails`, `analytics`, `briefReport`, `buh`, `licences` | `focus_lookup` | нет |
| `wildberries` | `stocks`, `orders`, `sales` | `wb_stocks`, `wb_orders`, `wb_sales` | нет |
| `ozon` | `products`, `stocks`, `postings` | `ozon_products`, `ozon_stocks`, `ozon_fbs_postings` | нет |

Принципы те же, что в 0.3: воронка сделки amoCRM проверяется по ответу системы; списки
фильтруются; всё, что попадает в адрес запроса, проверяется по шаблону; объём ответа ограничен.
Коннектор, не объявленный в `access.CONNECTORS`, не даёт шлюзу стартовать.

## Сверка с документацией и что не проверено

Методы сверены с официальной документацией на 6 октября 2026:
amoCRM API v4 (`/api/v4/leads`, `/api/v4/{leads|contacts|companies}/notes`, Bearer),
МойСклад JSON API 1.2 (`/entity/…`, `/report/stock/all`, Bearer, gzip),
Контур.Фокус API 3.0 (`/api3/{метод}?key=…&inn=…`, до 100 ИНН — шлюз ограничивает 10),
Wildberries Statistics API (`/api/v1/supplier/{stocks|orders|sales}`, лимит 1 запрос/мин),
Ozon Seller API (`/v3/product/list`, `/v4/product/info/stocks`, `/v3/posting/fbs/list`).

**Все тесты коннекторов — на заглушках.** Реальные кабинеты не подключались. Особенно стоит
проверить на живых данных версии методов Ozon (Ozon регулярно выпускает новые версии) и
формат ответа МойСклад в отчёте об остатках.

## Отложено в 0.4.x

Яндекс 360 от имени сотрудника (Диск, Почта, Календарь), Диадок, СБИС, группы пользователей.
