# 0.4.1: группы, Диадок, СБИС, Яндекс 360

## Группы пользователей

`rugw groups add <группа> <email>` — участники по email (человек может ещё не входить в шлюз).
Права выдаются на `group:<группа>` так же, как на роль или человека:
`rugw grants add group:sales amocrm 'lead:*' write`. Потолок роли действует и здесь.
Изменения состава действуют со следующего вызова.

## Служебные токены (Диадок)

Таблица `service_credentials` (миграция `0007`): значение только зашифрованное (те же ключи
`RUGW_TOKEN_ENCRYPTION_KEYS`), поколение для CAS — как у токенов сотрудников после проверки 0.3.
`rugw credentials rotate` перешифровывает и их.

## Диадок — только чтение

- Вход: OpenID Connect через `identity.kontur.ru`. Администратор выполняет `rugw diadoc login`
  (Device Authorization Flow: ссылка и код → вход учёткой Контура). Шлюз сохраняет refresh-токен.
- Контур выдаёт новый refresh при каждом обмене — он сохраняется условно по поколению. Если другой
  процесс уже обменял токен, шлюз перечитывает и повторяет; иначе — `RELOGIN_REQUIRED`.
- `GetMyOrganizations` вызывается с `autoRegister=false`: значение по умолчанию может
  зарегистрировать пользователя в организации — побочный эффект, недопустимый для чтения.
- Права (ресурс): `BoxId` ящика. Инструменты: `diadoc_boxes`, `diadoc_documents` (`POST /V4/GetDocuments`).

## СБИС — только чтение

- Вход `СБИС.Аутентифицировать` логином/паролем служебного пользователя → `X-SBISSessionID`.
  Сессия в памяти; при 401 — повторный вход (одна попытка). Не больше 5 сессий на пользователя СБИС.
- Права (ресурс): тип документа (`ДокОтгрВх`, `ДокОтгрИсх`, …). Инструмент `sbis_documents`.
- Ссылки на вложения и подписи не отдаются: по документации они действуют месяц и дают доступ к файлам.
- Тексты ошибок СБИС не передаются — только код.

## Яндекс 360 от имени сотрудника — только чтение

`RUGW_YANDEX360_SERVICES=disk,mail`; права Яндекса `cloud_api:disk.read`, `mail:imap_ro`
(в `RUGW_YANDEX_EXTRA_SCOPES` и в OAuth-приложении). Права шлюза (ресурс): `disk`, `mail`.

- **Диск** (`disk_list`, `disk_recent`, `disk_read_text`): токен сотрудника. Подписанная ссылка на
  скачивание модели не отдаётся; шлюз скачивает сам, только `https` на домене Яндекса, без токена
  сотрудника, только текстовые форматы и не больше 1 МБ.
- **Почта** (`mail_list`, `mail_read`): IMAP + XOAUTH2. Ящик открывается `EXAMINE` (только чтение),
  письма — `BODY.PEEK` (не помечаются прочитанными). Тема поиска передаётся IMAP-литералом,
  адрес и папка проверяются по шаблону — подстановка команд IMAP невозможна. Письма больше 5 МБ —
  только заголовки; HTML очищается до текста; вложения — только имена.
  В ящике сотрудника должен быть включён IMAP.
- **Календарь не реализован**: вход в CalDAV Яндекса по OAuth-токену официально не описан, все
  найденные решения используют пароль приложения. Писать вход наугад не стали.

## Сверка и что не проверено

Протоколы сверены с документацией на 8 октября 2026: Диадок — authentication, GetMyOrganizations,
GetDocuments V4; СБИС — sequence/auth, СБИС.Аутентифицировать, СБИС.СписокДокументов;
Яндекс Почта — OAuth для IMAP; Яндекс Диск — REST API.
**Все тесты — на заглушках и поддельном IMAP.** Особенно стоит проверить на живых данных:
значения `DocumentCategory` и формат дат в Диадоке V4, типы документов СБИС, имена папок Почты.
